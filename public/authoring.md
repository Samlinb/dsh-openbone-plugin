## Studio UI ownership

The DSH sidebar OpenBone entry opens the actual three-step workbench. Browser confirmations use the authenticated Studio endpoint; model production calls cannot impersonate them. For uiControlled projects inspect the reference first, then submit `review-character` with data `{assetId,checks:{recognizableSubject},subject,repairs,notes}` (recognizableSubject is boolean). Reject only when no recognizable character subject exists, such as pure scenery. Multiple characters, missing ears or limbs, occlusion and view inconsistencies are production repair tasks: select one subject, record its identity/location and repairs, include them in the parts plan, and reconstruct missing parts. Never reject a recognizable rabbit solely because another rabbit appears or an ear is missing. After parts are assembled, capture and review-static; wait for the user to confirm the loaded preview before creating animation or keyframes. A setup edit invalidates that confirmation. After a field error follow the explicit allowed/required list; do not repeatedly guess payloads.

## Three repeatable production steps

1. **Character.** Use `character` with character/style/production requirements, without planning parts yet. Generate with `concept` or import the user's PNG with `import-reference`. Inspect and show the image. Iterate until the user is satisfied, then select it with `reference`.
2. **Split and assemble.** Use `plan` to define parts, overlap, pivots and draw order. Generate/extract/reuse parts, build their actual scene with editor tools, and show `project_preview` to the user. Inspect a current time-zero `project_capture`: confirm visible appearance, layer order and joint connections. Revise parts, placement or plan as needed. Pass `review-static` only after inspection and the user's satisfaction.
3. **Motion.** Author and show animation, inspect key poses and loop seams, and repeat edits and `review-motion` until satisfactory.

`status` exposes `step` (1–3) and `stepName`. `revisit` with `{step:1|2|3}` reopens a step while retaining reusable assets; downstream reviews expire. Reconfirming the same reference preserves selected parts. Replanning the same character/style/projection keeps its reference and still-planned selections but requires another assembly review. Changing character identity resets active selections; immutable assets remain reusable. User satisfaction is obtained through conversation, not inferred from assistant checkboxes; these records do not authenticate a user approval.

# OpenBone creation guide

Use the OpenBone tools to author artwork and animation. The project lives on the hosted service. Shell files, an installed editor checkout and DSH configuration are not the bound project. Never inspect them to discover image paths. Start with openbone_prepare; bind or create a project if needed.

## References and artwork

Use `openbone_production` for new character production. Start with `operation: "status"`; every mutation supplies the returned `expectedVersion`, a stable `requestId`, and `data`. This is a durable workflow, not a checklist in chat.

1. `plan`: supply `character`, `style`, `production` (final `motion`, `projection`, `joints`, `layering`) and `parts`. Each part has `id`, `description`, normalized `pivot`, `parent` (another part ID or null), a concrete `overlap` requirement, and unique back-to-front integer `order`. Include final costume, proportions, expression, palette, hidden fill and joint coverage before the first paid image. Plan edits reset selections and reviews; use targeted repair for a single defect.
2. `concept`: generate one full-character appearance reference. Or `import-reference` with bounded `pngBase64` (PNG only, at most 1,500,000 Base64 characters). Poll/inspect the returned job. Ask the user to confirm the intended appearance when it is not already specified; do not claim confirmation that was not received. `reference` selects its `assetId` and records concrete appearance `notes`. These records explicitly remain assistant review, not authenticated user approval.
3. `generate-part`: supply only `partId` and a concise `instruction`. The server sends actual reference pixels to a reference-capable Qwen model. For repair, image 1 is the previously selected part to edit; image 2 is the character appearance reference only. A text-only provider is rejected before spending. Poll and inspect the candidate; `adopt-part` with `partId`, `assetId`, `notes` selects it after checking identity, edge quality, pivot and overlap. Existing assets or extracted crops can be adopted without generating again. Every other selected part remains unchanged, and replaced assets stay available for rollback by re-adopting the old ID. A candidate is never installed automatically. Use reject-part with partId, assetId and specific notes for semantically wrong candidates, even when their PNG checks passed.
4. Assemble selected parts with the editor tools. Read status after edits. Capture at `times:[0]`; then `review-static` supplies that `productionCaptureId`, `checks` containing booleans `consistency`, `overlap`, `occlusion`, `edges`, `pivots`, and specific `notes`. The server requires a current captured revision containing every selected image. False checks keep the stage in assembly. New animations/keys are blocked until this review passes.
5. Animate, capture at least first frame, an intermediate pose and the exact final loop time. `review-motion` supplies `captureId`, boolean `checks` (`poses`, `contacts`, `loop`) and findings. Compare contact points and keyframe data with pixels; the server verifies evidence identity, not artistic truth. Failed checks keep the motion stage open. Save the project and share normal-speed playback.

Asset replacement invalidates static and motion review. Setup edits invalidate both; motion edits invalidate motion review. Stale revisions, stale production versions, invented capture IDs and empty scenes cannot pass. Reference imports preserve original colors; green-key normalization applies only to generated cutout parts. Green materials need an alternative extraction/matting approach; do not misrepresent chroma key as general segmentation. Legacy sheet tools remain available for existing projects and tested extraction cases, but are not the default new-character production path.

Search relevant references and lessons once. An empty library is a normal state: continue original creation with this guide and report the reference gap. Do not import unrelated private references or treat a previous work's approval as approval of this character.

Legacy sheet mode only: when this method has been explicitly selected and tested, use one consistent sheet with up to nine parts. Default new production uses the reference-conditioned single-part workflow above. Specify species, projection, palette and outline style once. Split at joints that need independent motion; keep facial features with the head unless they must animate independently. Include overlap beyond pivots. Do not put green clothing or green body parts in a green-key sheet. Use a stable requestId, retain jobId and call openbone_assets_status with afterPoll equal to the latest returned pollCursor; the server handles the polling interval and bounded waiting. Each new poll uses the updated cursor, while replaying an old cursor only returns the observed state. Never use shell sleep for this workflow. Never generate again because a submission timed out; an unknown outcome requires reconciliation.

Inspect the original sheet AND normalized parts shown by openbone_assets_inspect before editing. Check the matte edges, that every cell contains the requested complete part, that body and limbs share a view, and that ears/limbs have enough overlap for rotation. Technical normalization detects empty cells and clipping, not semantic identity, anatomy or pivot correctness. A failed sheet needs a revised brief; never attach blank parts. Correct a declared pivot in the attachment placement if the actual joint differs from the brief.

When a complete part crosses a fixed grid boundary, or a single-part result contains several copies, use openbone_assets_extract to select one complete original-pixel rectangle with padding. Inspect returns the original sheet width/height. Extraction preserves the source, creates a separate asset with lineage and costs no image-generation call. Do not regenerate an entire good set merely to change crop boundaries. Use the cropped image's own dimensions and pivot when placing it on a bone.

After two semantically wrong sheets from the same model, report that model's instruction-following limitation and request an operator model change instead of repeatedly spending on similar prompts. Preserve running tasks and inspect their eventual outputs; an operator model change does not invalidate the existing job IDs.

## Rig and coordinates

Discover editing schemas, then query only the entities you need. Use assetId, never pngPath. Create bones, back-to-front slots and regions in a small atomic transaction with latest expectedRevision and stable requestId. Root motion belongs on a parent bone; secondary parts inherit body motion. Keep left/right limbs distinct when both silhouettes must appear.

Image pivots use normalized top-left coordinates [px,py]; images point down, skeleton y points up. A region's setup x/y positions its CENTER relative to its bone origin. For a chosen display size w,h, a non-rotated center offset is [(0.5-px)*w,(py-0.5)*h]. The full image cell is preserved, including transparent padding. Use one consistent pixels-to-world scale. Bone animation translations and rotations are offsets from Setup; scale keys multiply Setup. Do not treat key values as absolute poses. Verify the discovered schema's channel semantics.

Call openbone_project_capture at times:[0] to inspect a static assembled WebGL frame before adding many keys. Check joint contact, body proportions, draw order, projection and the overall silhouette. Fix materials or setup before animating a broken rig. Capture is a bound-project operation, not an arbitrary browser. Never read viewer HTML, curl resources or install/run browser commands from the creative chat. If prepare.previewCapture.available is false, report that operator configuration gap.

## Motion and review

Define observable stages and a short loop before adding keys. A jump normally includes anticipation, push-off, airborne motion, contact compression and recovery. Limb movement supports the contact phase; ears and tail follow the body's acceleration with a delay. Use a few clear key poses, then tune timing and curves. Do not substitute a single rigid image translated up and down for an articulated character.

Read back keyframe counts and duration, save the current project, and use openbone_project_capture with animationName and up to six key times to inspect actual WebGL frames. Inspect contact, highest point, compression and the first/last loop frames with a fixed camera. Give the exported viewer link to the user for normal-speed playback; still captures alone do not establish that you watched a full cycle. A generated link, successful export or HTTP 200 is not playback evidence. For headless hosts, playback:false and cleanPreview:false describe Java viewport features; exported WebGL playback remains available through openbone_project_preview and server capture is a separate configured capability.

After corrections, save again. Report the preview, saved revision, what was actually checked and any defects that remain. Keep technical checks, your visual observations and the user's approval separate. A stopped run should retain its job/asset IDs and last saved revision for continuation.

Capture images use a light checkerboard so transparent joint gaps stay visible. Rounded part endpoints must overlap actual opaque pixels inside the torso, with a margin through the full animated range. A touching bounding box is insufficient. Inspect the shoulder, neck and hip seams in every sampled pose before saying there is no separation; visible cut rings and conservative limb hiding remain quality defects to report and correct.




## Contour production (preferred)
After character confirmation and recognition, plan the independently moving parts. Inspect the reference once. Submit production split-masks with data {parts:[{partId,points:[[x,y],...],joint:[x,y]}]}. Coordinates are ORIGINAL image pixels, y down. Trace contours, not bounding rectangles. Include overlapping hidden joint coverage where original pixels permit. Submit all masks once; identical masks reuse immutable assets. assemble with data {} creates/updates and saves the real rig using original coordinates and layer order. Do not manually create each bone or guess placement.

For missing or defective areas, repair-local with {partId,points,instruction} uses selected-part LOCAL pixel coordinates. The server composites only within this polygon and preserves every pixel outside. The provider receives a guide, not a native mask API; review semantic alignment. prepare advances the durable pending repair; do not loop status/inspect. Limit two attempts per source asset. Inspect the resulting part and assemble again; capture time zero and review-static, then wait for browser user confirmation before motion. Never merge ears into head just to work around extraction.

Capture returns productionVersion: use it as expectedVersion when submitting the matching static or motion review. A rig edit advances production version. Report phase outcomes and defects, not a narrative for every poll or keyframe.
